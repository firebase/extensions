- fix: the README now recommends `.env.<projectId>` (or `.env.<alias>`) for instance config and has an Uninstall section. `firebase functions:kits:uninstall` only deletes deployed resources for a project with a `.env.<projectId>` (or `.env.<alias>`) file, so with the plain `.env` the README suggested before, it removed the instance from `firebase.json` and exited without an error but left the function running and sending mail. The new section also covers the `kit-<instance-id>-*` secrets and IAM role bindings that uninstall leaves behind.
- docs: correct the secret names the kit asks for. They are `kit-<instance-id>-SMTP_PASSWORD`, `kit-<instance-id>-CLIENT_ID`, `kit-<instance-id>-CLIENT_SECRET` and `kit-<instance-id>-REFRESH_TOKEN`, not the bare `SMTP_PASSWORD` and so on the README listed before. To reuse your extension's secrets, add a line such as `FIREBASE_SECRET_REF_SMTP_PASSWORD=ext-<instance-id>-SMTP_PASSWORD` to `.env.<projectId>`.

- fix: ship nodemailer 9, as extension 0.2.10 does. The kit shipped nodemailer 7, which fetched attachment URLs and OAuth2 tokens without checking certificates and dropped the part of a display name before a comma (`Doe, John <john@example.com>` became `John <john@example.com>`). With the SendGrid transport, the same address was sent as a `from` with name `Doe` and an empty address, and `to` gained an extra recipient with an empty address.
  Mail with an `https://` attachment `href` or `path` whose certificate is self-signed, expired, from a private CA or for another hostname now fails with `delivery.state: ERROR` (for example `self-signed certificate`), as it does in extension 0.2.10. `TLS_OPTIONS` does not change this, because it only applies to the SMTP connection. Fix the certificate, or fetch the file yourself and pass it as `content`. `http://` URLs and SMTP are not affected.
- fix: a template sent without `data` now renders with an undefined context, as in the extension. The kit passed `{}`, so `{{#if this}}` was true and `{{this}}` printed `[object Object]`.

- fix: invalid values in `.env` now fail the deploy instead of leaving mail unprocessed or quietly changing behaviour. The Firebase CLI only checks values it prompts for, so `TTL_EXPIRE_TYPE=days` deployed and left every document without a `delivery` field, `TTL_EXPIRE_VALUE=-1` set an `expireAt` in the past, and `AUTH_TYPE=oauth2` sent through the SMTP URI. The kit now rejects `DATABASE_REGION`, `AUTH_TYPE`, `OAUTH_SECURE` and `TTL_EXPIRE_TYPE` values that are not one of their options, and `SMTP_CONNECTION_URI`, `MAIL_COLLECTION`, `DEFAULT_FROM` and `TTL_EXPIRE_VALUE` values that fail the extension's format checks, as the extension did at install time. `DATABASE_REGION` is now case sensitive, as it was in the extension. Option labels such as `Day` are still accepted, as the extension accepted them, and run as they did in the extension. An empty `OAUTH_SECURE` now means `true`, as in the extension.

- fix: deploy `processQueue` with the extension's runtime settings: `concurrency: 1`, `cpu: "gcf_gen1"` (0.1666 vCPU at 256MiB) and `ingressSettings: "ALLOW_INTERNAL_ONLY"`. `setGlobalOptions` can't change these. Before, the kit took the 2nd gen defaults of concurrency `80`, 1 vCPU and `ALLOW_ALL`. A burst of mail with attachments landed on one 256MiB instance, which ran out of memory and dropped every event in flight on it: the documents were left in `PENDING` or `PROCESSING`, or with no `delivery` field, and were never retried or marked as failed, so the mail was never sent. Existing kit deployments switch on their next deploy.

- fix: an Eventarc publish failure no longer fails the function. A channel that was deleted or is unreachable answers `PERMISSION_DENIED`, and the publish was awaited before the work the function exists to do, so the mail was never sent. The publish failure is now logged as a warning and the invocation continues. Deploys also declare `eventarcpublishing.googleapis.com`, so the API is enabled on your project whether or not you use events.

- docs: the no-region fallback needs an explicit empty `DATABASE_REGION=` line in `.env`. Omitting the key entirely fails a non-interactive deploy, because the CLI resolves parameters before it reads their defaults. Corrects the note on the `DATABASE_REGION` mapping fix below; no behavior change.
- fix: restore the extension's `Yes` / `No` option labels on the `OAUTH_SECURE` deploy-time prompt. The stored values are unchanged (`true`/`false`), so this is a label-only fix and no `.env` from an earlier deploy needs editing.
- chore: run on firebase-functions ^7.3.3-rc.1, the same release candidate as the other kits
- fix: map `DATABASE_REGION` to a valid Cloud Run region before using it as the function region. Firestore multi-region locations (`nam5`, `nam7`) now deploy the function to `us-central1` and `eur3` to `europe-west1` instead of failing the deploy; regional locations pass through unchanged. The value is matched case-insensitively. With the parameter unset or empty the function declares no region and the Firebase CLI resolves one at deploy time.
